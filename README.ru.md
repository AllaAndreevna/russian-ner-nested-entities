# Извлечение именованных сущностей из русских новостей (NEREL): CRF и компактный трансформер под жёсткие ограничения

Учебный практикум (ИСП РАН), осень 2026. Задача: находить в русскоязычных новостных текстах именованные сущности
29 типов (PERSON, ORGANIZATION, PROFESSION, EVENT, DATE и др.), включая **вложенные** сущности, и возвращать их
границы и тип. Решение сдаётся в проверяющую систему с жёсткими ограничениями, поэтому проект - это не только
«обучить модель», но и инженерная работа в рамках бюджета по размеру и времени.

**Итог:** финальное решение - дообученный `rubert-tiny2` с общим энкодером и тремя «головами» для вложенных
сущностей и сжатой под лимит 16 МБ матрицей эмбеддингов. На закрытом тесте он даёт **macro-F1 0,5994**
(precision 0,603, recall 0,609): +0,035 к лучшему CRF (0,5645) и +0,065 к моему первому трансформеру (0,5346).
Путь к нему (плоский CRF → слои вложенности → трансформер, который сначала проиграл CRF → проверка гипотез,
объяснившая почему) описан ниже.

## Постановка и ограничения

| | |
|---|---|
| Данные | корпус NEREL v1.1 (русские новости, 29 типов сущностей, много вложенных) |
| Метрика | среднее по типам micro-F1 (macro по типам), совпадение границ и типа точное |
| Размер решения | архив ≤ 16 МБ |
| Время | ≤ 30 минут на тест, 8 CPU, 16 ГБ RAM, **без интернета** |
| Состав | `solution.py` с классом `Solution`, описание метода, код обучения и инструкция воспроизведения |
| Правила | тестовая часть корпуса не используется для обучения и подбора; не более 7 отправок в неделю |

Так как метрика усредняется по типам, редкие типы (LAW, CRIME, RELIGION, FAMILY, DISTRICT...) влияют на итог так же,
как частые (PERSON, DATE). Это определило многие решения ниже.

## Что было сделано и почему

### 1. Базовая модель и анализ потолка
Первая версия - линейная цепь CRF (`sklearn-crfsuite`) с ручными признаками (слово, префиксы/суффиксы, форма слова,
регистр, соседи в окне ±2) на плоской BIO-разметке. Результат: 0,469 на dev.

Прежде чем улучшать модель, я посчитала **потолок самой постановки**: если разметить dev «идеально», но в плоском BIO,
macro-F1 всего **0,854**. Причина - вложенные сущности (например, «Россия» внутри «Правительство России»):
плоская разметка теряет их по построению. Это показало, что ≈0,15 качества теряется ещё до модели.

### 2. Слои вложенности
Сущности сортируются по длине и жадно раскладываются по трём слоям так, чтобы внутри слоя спаны не пересекались
(внешние → вложенные → вложенные во вложенные; в train 29 709 / 6 507 / 1 019 сущностей по слоям). На каждый слой
обучается отдельный CRF (параллельно), предсказания объединяются. Потолок разметки вырос с 0,854 до **0,978**.
Эффект на тесте: **+0,08** macro-F1 (0,465 → 0,547). Дообучение на train+dev добавило ещё +0,018. Те же слои потом
использует трансформер: по одной классификационной «голове» на слой.

### 3. Диагностика ошибок и эксперименты с декодированием
В таблицах CRF precision заметно выше recall, то есть модель консервативна. Я проверила смещённое декодирование
(выбор тега по маргинальным вероятностям с порогом на класс `O`): на dev оно не помогло (0,560 → 0,556 и ниже),
поэтому в решение не вошло. Этот негативный результат тоже зафиксирован, чтобы не возвращаться к идее.

### 4. Первая попытка с трансформером под лимит 16 МБ
Чтобы поднять качество на редких типах, я дообучила предобученный `cointegrated/rubert-tiny2` (3 слоя, hidden 312).
Основная инженерная проблема - размер: словарь модели (83 828 токенов) занимает почти весь вес. В первой версии словарь
был обрезан до специальных токенов, коротких кусков (≤ 2 символов) и самых частых токенов обучающих текстов
(10-12 тыс.); остальные токены превращались в `[UNK]`. Веса хранились в fp16 (6,4 млн параметров, около 12 МБ).

Эта версия оказалась хуже CRF: 0,4956 → 0,5117 → 0,5346 на проверяющей системе после увеличения числа эпох и подбора
параметров, всё равно ниже 0,5645. На dev (без обучения на нём) она выходила на плато около 0,52 после ~10 эпох, хотя
лосс на обучении продолжал падать (в более поздних запусках F1 на части обучающих текстов доходил до ≈0,98 при ≈0,53 на
dev), то есть проблема была в обобщении, а не в недообучении. По типам она проигрывала CRF почти везде, особенно на
PERSON (F1 0,71 против 0,85), то есть на именах.

### 5. Проверка двух гипотез
Я сформулировала две гипотезы и проверила их скриптом `diagnose_vocab.py` и контролируемыми запусками на dev
(обучение только на train, seed 42, 15 эпох, lr энкодера 3e-4, batch 16):

| Запуск | Словарь | Эмбеддинг регистра | Эмбеддинги токенов | Macro-F1 dev: лучшая эпоха (15-я эпоха) | F1 PERSON (лучшая эпоха) |
|---|---|---|---|---|---|
| A | урезанный, 12 тыс. частых токенов | нет | полные | 0,5300 (0,5291) | 0,721 |
| B | урезанный, 12 тыс. частых токенов | да | полные | 0,5565 (0,5500) | 0,805 |
| C | весь (83 828 токенов) | нет | полные | 0,6105 (0,6068) | 0,868 |
| E | весь (83 828 токенов) | да | полные | 0,6134 (0,6134) | 0,875 |
| D | весь (83 828 токенов) | да | разложение ранга 64 | 0,5862 (0,5862) | 0,857 |
| F | только кириллица/латиница (83 303) | да | разложение ранга 96 | 0,6280 (0,6073) | 0,864 |
| G | только кириллица/латиница (83 303) | да | разложение ранга 128 | 0,6107 (0,6085) | 0,858 |
| - | CRF, 3 слоя (для сравнения) | | | 0,5600 | 0,850 |

В запусках C и E полная матрица эмбеддингов занимает ≈55 МБ (fp16), поэтому они только диагностические; в лимит 16 МБ
можно экспортировать запуски с разложением (D, F, G).

**Гипотеза 2 (обрезка словаря) - подтверждена.** При урезанном словаре в 12 тыс. токенов 19,7% кусков слов на dev
превращаются в `[UNK]`, а 43% всех эталонных сущностей (66% сущностей PERSON) содержат хотя бы один `[UNK]`. Полный
словарь даёт около +0,08 macro-F1 (A → C: 0,530 → 0,611) и поднимает F1 по PERSON с 0,72 до 0,87.

**Сжатие эмбеддингов.** Полная матрица эмбеддингов не помещается в 16 МБ, поэтому она заменяется низкоранговым
разложением (инициализация из предобученной матрицы через SVD) с экспортом в int8. Ранг 64 (77% энергии) уступает
несжатой модели примерно 0,025 (D против E); ранги 96 (83%) и 128 (88%) возвращаются на уровень несжатой модели
(0,61-0,63 против 0,61; разницы в пределах шума от эпохи к эпохе, около ±0,01-0,02 на dev). Ранг 96 - наибольший, что
помещается в лимит после экспорта в int8 (для ранга 128 оценка только весов около 15 МБ).

**Гипотеза 1 (потеря заглавной буквы) - в исходном виде опровергнута, но с полезным побочным результатом.** Токенизатор
различает регистр («Иван» и «иван» - разные токены). На урезанном словаре явный эмбеддинг регистра всё же помог
(A → B: +0,027 macro-F1, PERSON 0,72 → 0,81), а на полном словаре он ничего не добавляет (C → E: 0,6105 → 0,6134, в
пределах шума). Это согласуется с объяснением, что эмбеддинг в основном компенсировал информацию о регистре, потерянную
в токенах `[UNK]`: когда почти ничего не превращается в `[UNK]`, выигрыш исчезает. В финальной модели я его оставила,
потому что он ничего не стоит, но не утверждаю, что он там что-то даёт.

Оговорки: один seed; лучшая эпоха выбирается по dev, так что числа лучшей эпохи слегка оптимистичны (в скобках числа
последней эпохи показывают разброс); разницы меньше примерно 0,01-0,02 не стоит переоценивать.

### 6. Финальная модель
Финальная модель объединяет выводы: весь словарь из кириллицы и латиницы (83 303 из 83 828 кусков; куски других
алфавитов превращаются в `[UNK]`), низкоранговое разложение матрицы эмбеддингов ранга 96 (инициализация SVD, экспорт
в int8 с масштабом по строкам), эмбеддинг регистра и общий энкодер с тремя головами для слоёв вложенности. Около 12,7 МБ
весов; позиционные эмбеддинги обрезаны до 512, остальное хранится в fp16. Обучение на train+dev, 13 эпох (после ~10-й
эпохи кривая на dev плоская).

**Macro-F1 на тесте: 0,5994**, при сбалансированных precision и recall (0,603 / 0,609), против 0,5645 у лучшего CRF.
F1 на dev по ряду типов, CRF и трансформер (оба обучены только на train; единичные запуски):

| Тип | CRF | Трансформер |
|---|---|---|
| PERSON | 0,850 | 0,864 |
| PROFESSION | 0,684 | 0,726 |
| ORGANIZATION | 0,601 | 0,641 |
| COUNTRY | 0,770 | 0,851 |
| DISEASE | 0,317 | 0,638 |

| LAW | 0,414 | 0,534 |

Выигрыш сосредоточен на редких типах и именах, как я и рассчитывала; на WORK_OF_ART и LOCATION трансформер по-прежнему
хуже - это известное слабое место и повод рассмотреть ансамбль.

## Конфигурации и гиперпараметры

### CRF (`train.py`, `solution.py`)
| Параметр | Значение |
|---|---|
| Алгоритм | L-BFGS, `all_possible_transitions=True` |
| Регуляризация | c1 (L1) = 0,05, c2 (L2) = 0,02 (флаги `--c1`, `--c2`) |
| Итерации | 150 (`--iters`) |
| Отсечение редких признаков | `min_freq` = 2 (`--min-freq`) |
| Слои вложенности | 3, отдельный CRF на каждый, обучаются параллельно в процессах |
| Токенизация | `razdel` (предложения и слова), смещения пересчитываются в символьные |
| Размер моделей | 6,05 + 3,09 + 0,84 = 9,99 МБ; обучение ≈ 11 минут на CPU, предсказание на dev 6 с |

Признаки токена: слово в нижнем регистре, стем (русский Snowball из `nltk`, работает без внешних данных),
префиксы 2-3 и суффиксы 1-4 символа, форма слова (`Xxxx`, `dd`), регистр / верхний регистр / цифры / только буквы,
длина (не более 12), первое и последнее слово предложения, биграммы с соседним словом; для соседей в окне ±2:
слово, стем, суффикс из 3 символов, форма и регистр.

### Трансформер (`bert_train.py`, `solution_bert.py`)
| Параметр | По умолчанию | Строка 6 (первая версия) | Финальная (строка 7) |
|---|---|---|---|
| Базовая модель | `cointegrated/rubert-tiny2` (3 слоя, hidden 312, 12 голов внимания) | то же | то же |
| Данные | train | train+dev | train+dev (`--train-on-dev`) |
| Эпохи | 10 | 22 | 13 |
| lr энкодера / голов | 1e-4 / 1e-3 | 3e-4 / 1e-3 | 3e-4 / 1e-3 |
| Batch | 32 | 16 | 16 |
| Словарь | 10 000 частых токенов + короткие куски | 12 000 частых + короткие куски | все куски из кириллицы и латиницы, 83 303 (`--ru-en-vocab`) |
| Эмбеддинги токенов | полные | полные | разложение ранга 96, инициализация SVD, экспорт в int8 (`--emb-rank 96 --quantize-emb`) |
| Эмбеддинг регистра | выкл. | выкл. | вкл. (`--case-emb`) |
| Вес класса `O` в лоссе | 1,0 | 1,0 | 1,0 |
| Оптимизатор | AdamW, weight decay 0,01, linear warmup 6% шагов и линейный спад, clip градиента 1,0 | то же | то же |
| Прочее | dropout 0,1 в головах, seed 42, куски ≤ 80 слов и ≤ 512 позиций | то же | то же |

Лосс - сумма кросс-энтропий по трём слоям, считается на первом подтокене каждого слова. Объём обучающей выборки:
7 927 кусков (train) и 9 067 (train+dev). Одна эпоха занимает около 9 секунд на GPU в Colab. Точные параметры обученной
модели записаны в `bert_meta.json` (`train_args`).

## Инженерные уроки
- Метрика и потолок постановки считаются **до** выбора модели: это сразу показало, что главный рычаг - вложенность.
- Когда трансформер проиграл CRF, я не стала просто подбирать параметры: сравнила кривые обучения и dev, разобрала ошибки
  по типам, сформулировала гипотезы и написала скрипт (`diagnose_vocab.py`), который измеряет механизм без обучения.
  Одна гипотеза подтвердилась, другая была опровергнута, и обе повлияли на то, что я строила дальше.
- Каждое решение сверялось на dev по формуле метрики из условия (macro по типам, строгое совпадение границ); на тест
  отправлялись только проверенные архивы.
- Скрипт `check_submission.py` распаковывает архив во временную папку и запускает его так, как это делает проверяющая
  система (проверка структуры, импорта, формата ответа и времени): он ловит ошибки упаковки до отправки.
- Бюджет по размеру нужно считать явно: оценка размера без учёта экспорта в int8 однажды подсказала, что вариант не
  влезает, хотя он влезал; теперь скрипт обучения печатает ожидаемый размер для выбранных флагов.
- Практические грабли: `crfsuite` на Windows не сохраняет модель в папку с кириллицей в пути (молча не пишет файл);
  новая загрузка Hugging Face через Xet может быть недоступна в корпоративной сети; смещения символов ломаются, если
  читать текст без `newline=""`.

## Использование релиза
Обученная модель опубликована в разделе **Releases** как `submission_bert.zip` (тот самый архив, что был отправлен в
проверяющую систему). Распакуйте его и используйте класс `Solution` (достаточно CPU; Python 3.10, `torch`,
`transformers`, `tokenizers`, `razdel`):

```python
from solution import Solution          # solution.py из распакованного архива

sol = Solution()
texts = ["Президент выступил в Москве на встрече с министрами."]
for text, entities in zip(texts, sol.predict(texts)):
    for start, end, entity_type in sorted(entities):
        print(entity_type, repr(text[start:end]))
```
`predict` возвращает для каждого текста множество кортежей `(start, end, type)` со смещениями `[start, end)` в символах.

```bash
# Данные: скачать NEREL v1.1 (https://github.com/nerel-ds/NEREL), положить папки train и dev
# (файлы *.txt и *.ann) в data/train и data/dev. Папку test для обучения не использовать.

# CRF: подбор на dev, затем финальная модель на train+dev
python train.py --data-dir data
python train.py --data-dir data --train-on-dev

# Трансформер, финальная конфигурация (интернет нужен один раз, чтобы скачать модель; GPU ускоряет обучение)
python bert_train.py --data-dir data --epochs 13 --lr 3e-4 --batch-size 16 --ru-en-vocab --case-emb --emb-rank 96 --quantize-emb --train-on-dev
# Те же флаги без --train-on-dev и с --no-save оценивают конфигурацию только на dev.

# Сборка архива и локальная проверка
python make_bert_zip.py
python check_submission.py submission_bert.zip data/dev
```
Для CRF-архива: `python -m zipfile -c submission.zip solution.py model_0.crfsuite model_1.crfsuite model_2.crfsuite description.txt train.py`.
Путь к проекту лучше задавать латиницей.

## Данные и лицензии
Корпус NEREL распространяется его авторами (https://github.com/nerel-ds/NEREL), условия использования смотрите там.
Предобученная модель: `cointegrated/rubert-tiny2` на Hugging Face; опубликованные веса дообучены из неё, поэтому
перед повторным использованием проверьте её лицензию на странице модели.
